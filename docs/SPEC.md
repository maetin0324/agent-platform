## 1. 何のために作るか

**複数の案件を同時に抱えたときに、楽になるため。**

k8s 上のアドホック FS 研究の妥当性検証、自分の考えた最強のトレースシステムの開発、クラスタの管理仕事 — こういうものを
同時に抱えたとき、秘書にあれこれ言い、各所から上がってくる報告を高速で流し見し、必要なところにだけ口を出す。
それで回るようにする。

## 2. 使う場面

### 2.1 実装の案件を投げる

「brainfuck インタプリタを作れ」と投げる。終わったとき、`~/workspace/rust/brainfuck` のような**普段のパス**に
コードベースができていて、**そのまま GitHub に公開できる形**になっている（パスは rust なら `rust/hoge`、研究なら
`lab/fuga` のように、気分で決められる）。

### 2.2 調査の案件を投げる

「○○の関連研究を調べて」と投げる。終わったとき、GUI から**調査結果の文書**と**見るべき関連研究へのリンク**が
まとまって読める。

### 2.3 抽象的な研究の案件を投げる

「これとこれを組み合わせた研究がしたい」くらい曖昧な依頼を投げる。それが
関連研究調査 → 実装の計画立案 → 実験計画の構成 → クラスタへの投入 → デバッグ → レビュー → 論文執筆
のような種々の仕事に分解され、実行される。

その途中で、**どの粒度にも口を出す**。「実装ではこういうトレイトを切れ」という細かい指示から、
「そもそも全体のアイデアを議論しよう」という上流の話まで。

### 2.4 悪い知らせが来る

クラスタ管理をやらせていると「ここの脆弱性がヤバい」「このノードが落ちた・壊れた」という報告が上がってくる。
良い知らせと同じ経路で、目立つ形で届く。

## 3. 登場するもの

### 3.1 秘書

あなたの相手。案件を受け取り、組織に流し、報告を集めてあなたに渡す。
**部をまたぐ連携は秘書が認める**（秘書が統制しないと情報が錯綜する）。

### 3.2 組織（一つだけ。役割の木）

組織は一つ。得意分野ごとにざっくり分かれている。最初の形はあなたが描いたもの:

```
秘書
├── コーディング部
│   ├── フロントエンドデザイン課
│   ├── パフォーマンス課
│   └── PoC・R&D 課
├── 研究部
│   ├── 関連研究調査課
│   ├── 論文執筆課
│   └── データ整理課
└── インフラ部
```

- 途中で役職を足す・分ける・消すことはできる（私の解釈: あなたが GUI から組織図を編集する）。
- **各ノードは「人」**。長期記憶を持ち、複数の案件の仕事を並列に抱える。
- 記憶は**案件をまたぐ**。特定クラスタのジョブ投入方法、あなたの研究分野・興味の方向性、直近で相談した内容など。
  （私の解釈: 案件固有のこと — このリポジトリのこのトレイト — も覚えるが、それは案件の引き出しに入る。）

(追記) 全ての人を単一のハーネスで表現するのではなく用途に応じてハーネスを使い分ける。
codingの場合はclaude codeやopencode, 今あるgenreはこれのイメージで特化ハーネスにLLM sourceからのAI能力を注入する感じ

### 3.3 案件と、仕事の木（DAG）

案件は組織の上から入り、分解されて下へ流れる。分解された仕事の依存関係が**仕事の木**。
これを**パッと見れば、おかしな方針を立てていないかが分かる**のが目的。

### 3.4 口出し

おかしなことをしていたり、追加の指示を出したいとき、**組織の木を見て「誰に言うか」を決め、その担当に直接言う**。
相手は「人」なので、先週の議論の続きとして話せる。

### 3.5 報告

上に行くほど**多くのレビューが入り、圧縮される**。だから上で見る報告はパッと見の判断が楽。
良い報告の例（あなたの言葉）:

> ここまで作業が進み、この程度の結果が確認できました。またこの結果から、このような framing で論文執筆が可能だと思われます。

悪い報告の例:

> ここが脆弱性ヤバいです。 / このノード落ちました、壊れました。

通知は GUI から飛んでくる。**数分単位ではなく、数時間単位**。

### 3.6 認可

**少しでも聞くべきだとエージェントが判断したら、あなたに指示を仰ぐ。**
あなたはそれに対して「今回だけ」か「同じようなことは今後ずっと」のどちらかの認可を出す。
永続の認可は文字で記録してエージェントに注入する。自動判定・自動化できるものはする。

### 3.7 成果物の置き場所

人が普段見る場所に、普段の形で。コードは `~/workspace/…` のリポジトリ、文書は GUI で読める形。
どうしても必要なら VS Code や論文を直接見に行くが、**基本は GUI から確認して楽をする**。
(追記)既存のコードベースを扱う案件やいろんなクラスタ、作業環境にコードがクローンされている場合は手元で編集してリモートで検証を行ったりなどをする。リモートからは必要以上にファイルを転送させず、基本コードと必要に応じて検証結果データなどを持ってくる

## 4. 画面（GUI が基本）

見えるもの:

1. **秘書との対話** — 案件を投げる、状況を聞く、方針を変える。
2. **組織の木** — 誰が何を抱えているか。ノードを選ぶとその「人」に直接話せる。
3. **仕事の木（DAG）** — 案件ごとの分解と進み具合。方針の異常を一目で。
4. **報告の流れ** — 各所から上がってくる報告を高速で流し見する。良い知らせも悪い知らせも。
5. **認可の要求** — 聞かれたことに「今回だけ / 今後ずっと」で答える。永続の認可の一覧と編集。
6. **成果物** — 調査文書・リンク集はここで読む。コードは置き場所へのリンク。

今回は最初から GUI で使う形で作る、サーバー側は今のCLIの実装を流用してどうにかする


## 5. 決めごと

- 組織は一つ。部をまたぐ連携は秘書の認可を通す。
- ノードは長期記憶を持ち、案件をまたいで覚える。
- 迷ったら聞く。認可は「今回だけ / 今後ずっと」。永続認可は記録して注入、可能なら自動化。
- 報告は上に行くほどレビューと圧縮。通知は数時間単位。
- 成果物は人が普段見る場所に、公開できる形で。

## 6. 最初の一本

**「Pluvio を基盤に用いた新たな研究テーマの模索、検証」**

（Pluvio: あなたの Rust ライブラリ。benchfs や集団通信ベンチの基盤になっている、と私は理解している。
違っていれば一行で直してほしい。）
(追記: Pluvioはad-hoc FSのI/Oサーバを効率化するための非同期ランタイム基盤、研究のメインテーマの一つでIEEE Cluster 2026 Best Paper Finalistに選ばれている)

この一本で通したいこと（私の解釈。§7 で確認する）:

1. 秘書に上の一文を投げる。
2. 研究部（関連研究調査課）が Pluvio の周辺と隣接分野を調べ、候補テーマをいくつか挙げる。
3. あなたが候補に口を出す（「これは面白い」「これは既にある」「この方向で深掘り」）。
4. 選ばれたテーマについて、コーディング部（PoC・R&D 課）とインフラ部がクラスタで小さな検証を回す。
5. 研究部が結果をまとめ、「この framing で論文が書けそう」まで含めた報告が秘書経由で上がってくる。
6. 調査文書・候補テーマ・検証結果が GUI で読め、検証に使ったコードが `~/workspace` に残る。

## 7. まだ決めていないこと

- **Pluvio とは何か**、一行で。
  - Pluvioはad-hoc FSのI/Oサーバを効率化するための非同期ランタイム基盤、研究のメインテーマの一つでIEEE Cluster 2026 Best Paper Finalistに選ばれている
- **「検証」の合格線**。候補テーマが「検証できた」とは、何が示せたときか（性能の数字？ 動くデモ？ 既存研究との差分の言語化？）。
  - 必要に応じて判断するが、こちらからアイデアや仕事を秘書に投げかけて相談しながら決める、途中目標はここまでできたら一旦教えて欲しいなども
- 秘書があなたに**最初に聞いてくること**は何か（予算？ 締切？ 使ってよいクラスタ？）。
  - 案件の理解確認、大まかな方針と最初の途中目標の提案・相談
  - 途中目標は予め大まかに決めておいて、適宜再設計する
- 案件の**終わり**は誰が決めるか（あなたが「もういい」と言うまで続く？ 秘書が「ここまで」と提案する？）。
  - 途中目標の達成ごとに判定する、いい感じだったら承認し次の途中目標までのGoサインを出すか、途中目標の再設計を考える。アジャイル開発のイメージ

## 8. 今あるものの扱い（あなたの判断）

あなたの評価では、**仕事の木・分野・ssh の自動接続**は「ほんの一部だけ思っていた形」になっている。
それ以外 — タスクの状態機械を中心にした設計、CLI、今の GUI の画面構成 — はこの仕様に合っていない。

- 流用の候補: 仕事の木（DAG）、分野ごとのハーネス、クラスタへの接続、アカウントの切り替えと予算の観測。
- 捨てる候補: 「タスク」を単位にした状態機械と、それを前提にした画面・CLI。

どれを残しどれを捨てるかは、この文書に納得してもらってから、あなたと決める。

(追記) LLM sourceを一つにまとめて、要求する能力と登録済みアカウントの予算とのバランスでいい感じにLLM sourceを振り分ける。
claude は claude code, gptはcodexのようにするのではなく適宜用途に応じたハーネスに振り分ける。無料で無限に使えるpegasus上のQwen3.8-27Bをいろんなハーネスに注入できるようにclaudeやgptもいろいろ注入する。LLM sourceという抽象レイヤ（現在の実装でいうプロバイダ？）
