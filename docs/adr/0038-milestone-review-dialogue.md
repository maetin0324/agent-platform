# ADR-0038: 途中目標の判定は「結果の報告 → 次の提案 → ok / 議論 / ng」の対話にする

- 日付: 2026-09-18
- 状態: **Accepted**（人間の依頼「途中目標達成でこちらに指示を仰ぐ、受け入れか拒否か決める際に、追加の指示を与えて次の途中目標の
  決定に関与する余地を作って下さい。『この方針で進めてもいいですか？ ok or ng』だけではなく『この途中目標まででこのような結果が
  得られました、なので次はこのような方針を考えていますがどうでしょうか？』という聞き方に対して、全く問題が無ければ ok、
  途中結果に対する議論が必要な場合は議論、全くダメな場合は ng」）
- 関連: SPEC §7（途中目標ごとに人が判定し、Go か再設計。アジャイル）/ §3.1 / §3.4、ADR-0033 D2（milestones）/ D4（対話）、
  ADR-0037（`milestone_ready` の通知）、ADR-0034 D7（結果ファイルの宣言的フィールド）

## 1. 文脈

今日の実機で、途中目標「隣接領域の動向調査」の 2 つの調査が終わり、次の仕事が Go 待ちで止まった。人に届いたのは
「done 2、Go 待ち 2。達成の判定と次の Go をお願いします」という**状態の通知**で、**何が分かったか**も**次に何をするつもりか**も
無い。人は GUI で `answer.md` と `report.md` を読み、自分で次を考えなければならない。SPEC §7 が言う「途中目標の達成ごとに判定し、
いい感じなら承認して次の途中目標までの Go サインを出すか、途中目標の再設計を考える」は、**秘書が結果をまとめて次を提案し、
人がそれに答える**形でないと成立しない。

## 2. 決定

### D1. 途中目標の仕事が止まったら、秘書が「途中目標レビュー」の対話 run を 1 回起こす

- 条件は ADR-0037 D5 の `milestone_ready` と同じ（動いているものが無く、done が 1 件以上、`reached` でない）。**通知の前に**この run を起こす。
- run は**対話 run**（Phase 28/30 の規則: 対話用ハーネス、委譲も Question も不可、記憶と直近の仕事を前置き）。
  前置きに加えて**その途中目標の仕事の成果**を入れる: 各タスクの title / status / 終端の要約 / 主な成果物（`answer.md` / `report.md` は
  先頭 4,000 字。決定的に切る）。
- 指示文（プロンプトの仕事。コードは結果を受け取るだけ）:
  「途中目標『X』の仕事が止まりました。人に向けて (a) この途中目標までで**得られた結果**の要約（数字・候補・出典）、
  (b) 達成と言えるか（言えないなら何が足りないか）、(c) **次の途中目標の提案**（1 つ。題名と説明）、(d) 判断を仰ぎたい点、を
  数十秒で読める分量で書け。次の途中目標は結果ファイルの `milestone_proposal` にも書け。」
- 返事は `messages`（秘書、案件）に入る。結果ファイルの **`"milestone_proposal": {"title": "...", "description": "..."}`**
  （ADR-0034 D7 と同じ宣言的フィールド。無ければ提案無し）から、taskd が**決定的に** `milestones` に `status = proposed` の行を
  1 件作る（`seq` は末尾）。この run の `task` は `support = "milestone_review"`（裏方）。
- `milestone_ready` の Discord 通知は**この返事が付いてから**送り、文面に返事の先頭 300 字を含める（「結果 → 提案」が手元で読める）。

### D2. 人の答えは 3 つ: **ok / 議論 / ng**（自由記述を添える）

`POST /milestones/{id}/decide {decision: "ok" | "discuss" | "ng", note?: string}`（管理系）

| 答え | taskd がすること（決定的） |
|---|---|
| `ok` | この途中目標を `reached`。提案された次の途中目標（`proposed` の最新）を `approved` にし、**その途中目標の計画 run を起こす**（`POST /projects/{id}/plan` と同じ経路。`note` は計画の `note` に渡る）。`note` は秘書への `messages`（`role = user`）にも残す |
| `discuss` | 何も変えない。`note` を秘書への対話として送る（`POST /org/secretary/messages` と同じ）。秘書の返事に**新しい `milestone_proposal` があれば**、`proposed` の途中目標を**差し替える**（古い提案は `redesigned`）。人は納得したら `ok` を押す |
| `ng` | この途中目標を `redesigned`（達成にしない）。提案された次の途中目標も `redesigned`。`note`（理由）を秘書への対話として送り、秘書に**この途中目標自体の再設計**（やり直す／別の切り方）を提案させる。返事の `milestone_proposal` は `proposed` の新しい途中目標になる |

- `note` は 3 つとも任意だが、`discuss` と `ng` では**空なら 422**（議論・拒否の理由が無いと秘書が動けない）。
- `ok` で起きる計画 run は従来どおり `draft` の仕事を作る（人の Go は従来どおり。SPEC §7）。

### D3. GUI（案件画面の途中目標カード）

- 途中目標が `milestone_ready` の状態（秘書のレビューの返事あり）なら、カードに**秘書の返事（Markdown）**と、
  **提案された次の途中目標**（題名・説明）、そして **「ok」「議論」「ng」** の 3 ボタンと自由記述欄を出す。
- `ok` → 「達成にして、次の途中目標を承認し、分解を秘書に頼みました」。`discuss` → 秘書の対話画面（案件を選んだ状態）へ遷移し、
  返事を待つ（新しい提案が付けばカードが差し替わる）。`ng` → 理由必須。「達成にせず、再設計を秘書に頼みました」。
- レビューの返事がまだ無い（run 中）なら「秘書が結果をまとめています」。

### D4. Discord の文面（ADR-0037 D1 の `milestone_ready` を改める）

「途中目標『X』の仕事が止まりました。秘書のまとめ: <返事の先頭 300 字>… → 案件で **ok / 議論 / ng** を選んでください」＋案件へのリンク。

## 3. 採らない

- 人の答えを秘書の LLM に解釈させる（ok / ng を自然文から判定する）。3 値は人が押す。自由記述は秘書への言葉として渡すだけ。
- 途中目標の達成を LLM が決める。**達成にするのは人の `ok` だけ**（秘書は「達成と言えるか」を提案するにとどまる）。
- 次の途中目標を自動で承認して分解まで進める。`ok` を押すまで何も動かない。

## 4. 受け入れ条件（Phase 41 / G13j）

1. `milestone_ready` の状態で秘書のレビュー run が 1 回だけ起き（裏方 `milestone_review`）、返事が `messages` に入り、
   `milestone_proposal` から `proposed` の途中目標が 1 件できる。通知は返事の後、文面に要約が入る。
2. `decide`: `ok` → `reached` + 次を `approved` + 計画 run（`draft` の仕事ができる）／`discuss` → 対話が送られ、新提案で差し替わる／
   `ng` → `redesigned` + 再設計の対話。空の `note` は `discuss` / `ng` で 422。管理系 401（両構成）、404、409（`reached` 済み等）。
3. GUI のカード（返事・提案・3 ボタン・自由記述、run 中の表示）。
4. **実機**: いま止まっている途中目標「隣接領域の動向調査」で、秘書のまとめが届き、人が `ok` / `議論` を実際に押して次が動く。
5. `cargo test --workspace` / clippy / GUI 一式。
